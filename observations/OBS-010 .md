# OBS-010 — `String.toInt()` passes semantic checking but fails at runtime

## Status

CONFIRMED

## Classification

Compiler / runtime consistency

## Severity

Relevant to normal application development.

The issue does not prevent basic Kof programs from executing, but it blocks
the investigated path for converting textual user input into integer values.

## Context

During EXP-001 F4.4, standard input was successfully obtained using:

```kof
var line = readLine()
```

Because `readLine()` produces textual input, the calculator requires a
conversion from `String` to `Int`.

Initial inspection of examples and implementation did not identify an obvious
documented conversion API.

A direct probe using the natural `toInt()` form was therefore performed.

## Probe

File:

```text
src/numeric_conversion_probe.kf
```

Source:

```kof
main() {
    var value = "10".toInt()
    println(value)
}
```

## Semantic check

Command:

```powershell
..\Kof4j\dist\kof-0.0.7-alpha-windows-x86_64\bin\kof.bat check .\src\numeric_conversion_probe.kf
```

Observed result:

```text
checked 1 file(s) ? no errors
```

### Result

**PASS**

The checker accepts the expression:

```kof
"10".toInt()
```

No semantic diagnostic is emitted.

## Runtime execution

Command:

```powershell
..\Kof4j\dist\kof-0.0.7-alpha-windows-x86_64\bin\kof.bat run .\src\numeric_conversion_probe.kf
```

Observed result:

```text
Exception in thread "main" java.lang.NoSuchMethodError:
'java.lang.Object java.lang.String.toInt()'

    at Default.Main.main(numeric_conversion_probe.kf:2)
```

### Result

**FAIL**

## Observation

There is a reproducible discrepancy between `kof check` and JVM runtime
behavior.

The expression:

```kof
"10".toInt()
```

passes semantic checking but cannot execute successfully.

The runtime error reports an attempted invocation equivalent to:

```text
java.lang.String.toInt()
```

which is unavailable on the runtime `String` type.

Therefore:

```text
Kof source
   |
   v
"10".toInt()
   |
   +-----------------------+
   |                       |
   v                       v
kof check               kof run
   |                       |
   v                       v
 PASS                  NoSuchMethodError
```

## Why this matters

A user relying on `kof check` receives no indication that this program will
fail when executed.

The problem is therefore different from an unsupported operation correctly
rejected by the compiler.

The tested expression crosses the semantic-check boundary successfully and
fails only after execution begins.

For tooling and developer experience, this means that at least one expression
accepted as semantically valid by the tested compiler does not correspond to
a valid JVM runtime operation.

## Impact on EXP-001

F4.4a established that:

```kof
readLine()
```

works correctly.

However, the calculator needs numeric operands.

The investigated path:

```text
stdin
  ↓
readLine()
  ↓
String
  ↓
toInt()
  ↓
Int
```

currently fails at the final conversion step.

Consequently, the interactive calculator is temporarily blocked while other
supported conversion mechanisms are investigated.

This observation does **not** establish that Kof has no working
`String → Int` conversion.

It establishes specifically that the tested `String.toInt()` expression:

1. is accepted by `kof check`;
2. produces no semantic error;
3. fails during JVM execution;
4. produces `NoSuchMethodError`.

## Reproducibility

Tested with:

```text
Kof: 0.0.7-alpha
Target: windows-x86_64
JVM: Eclipse Adoptium 21
Host: Windows
```

Minimal reproduction:

```kof
main() {
    var value = "10".toInt()
    println(value)
}
```

Then:

```powershell
kof check numeric_conversion_probe.kf
```

followed by:

```powershell
kof run numeric_conversion_probe.kf
```

Expected from observed behavior:

```text
check -> PASS
run   -> java.lang.NoSuchMethodError
```

## Evidence strength

**HIGH**

The behavior was reproduced directly using a minimal source file, with
separate checker and runtime executions.

No modification to the Kof compiler or runtime was made to produce the
result.

## Follow-up

Investigate whether another officially supported conversion mechanism exists,
including alternative constructor/conversion syntax.

Do not classify general `String → Int` conversion as unsupported until those
paths have been evaluated.

## Final status

**CONFIRMED — OPEN FOR FOLLOW-UP**
