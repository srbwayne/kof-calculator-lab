# OBS-004 — CRLF conversion breaks source packaging on Windows

Category: TOOLING / WINDOWS / LINE ENDINGS
Status: CONFIRMED + MITIGATED

## Context

The Kof4j frozen snapshot was checked out on Windows with:

    core.autocrlf=true

Git reported LF files being materialized with CRLF in the working tree.

Relevant examples included:

    VERSION
    scripts/package.sh

## Initial behavior

Running:

    bash scripts/package.sh --skip-build

failed while processing the shell script.

The first observed failure was associated with:

    set: pipefail

After normalizing `scripts/package.sh` to LF, execution progressed
further but subsequently produced a path containing:

    kof-cli-0.0.7-alpha$'\r'.jar

## Diagnosis

`VERSION` was still materialized as CRLF.

The carriage return became part of the version value consumed by
the packaging script.

## Controlled mitigation

Only the relevant working-tree files were normalized from CRLF to LF.

No logical source changes were made to Kof.

After normalizing:

    scripts/package.sh
    VERSION

the packaging script progressed successfully.

## Conclusion

Windows checkout line-ending conversion can affect files consumed
directly by the Kof source packaging workflow.

The issue is not limited to shell-script parsing: CRLF in textual
inputs such as `VERSION` can propagate carriage-return characters
into derived paths and artifact names.

## Potential future improvement

Consider explicitly protecting line-ending-sensitive repository files
through `.gitattributes` and/or documenting the required checkout
configuration.

Do not classify as an upstream defect yet.
