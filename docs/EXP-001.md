# EXP-001 — Kof Calculator Language Probe

## Status

IN PROGRESS

## Objective

Evaluate Kof 0.0.7-alpha through the incremental construction of a small
calculator.

The experiment is intentionally exploratory.

Its purpose is not only to determine whether a calculator can be implemented,
but also to observe the language, compiler, CLI, runtime behavior, developer
experience, diagnostics, and inconsistencies encountered while building a
small real program.

## Environment

- Host OS: Windows
- Shell: PowerShell
- Kof version: 0.0.7-alpha
- Kof target: windows-x86_64
- JVM: Eclipse Adoptium 21
- Kof source: Kof4j upstream repository
- Execution: packaged Kof distribution
- Repository under test: `kof-calculator-lab`

## Method

The experiment evolves in small probes.

For each relevant language capability:

1. inspect existing Kof examples when necessary;
2. create the smallest useful source file;
3. execute `kof check`;
4. execute `kof run` when the source passes checking;
5. record observed behavior;
6. preserve unexpected behavior as an observation;
7. avoid modifying Kof itself to make the experiment pass.

A successful `check` is not assumed to imply successful execution.

## F4.2 — Operation dispatch

A calculator dispatch function was introduced using the control-flow syntax
supported by the language.

```kof
calculate(Int a, Int b, String operation): Int {
    if (operation == "+") {
        return add(a, b)
    } else {
        if (operation == "-") {
            return subtract(a, b)
        } else {
            if (operation == "*") {
                return multiply(a, b)
            } else {
                return divide(a, b)
            }
        }
    }
}
```

Probe:

```kof
main() {
    println(calculate(10, 2, "+"))
    println(calculate(10, 2, "-"))
    println(calculate(10, 2, "*"))
    println(calculate(10, 2, "/"))
}
```

Observed output:

```text
12
8
20
5
```

Result:

**PASS**

## F4.4 — User input

### F4.4a — `readLine()`

A direct standard-input probe was created:

```kof
main() {
    println("Enter something:")
    var line = readLine()
    println("You entered: " + line)
}
```

`kof check` accepted the source.

Interactive execution with:

```text
hello kof
```

produced:

```text
Enter something:
hello kof
You entered: hello kof
```

Result:

**PASS**

Standard input is therefore available through the public `readLine()`
function in the tested JVM execution path.

### F4.4b — `String` to `Int`

The calculator requires conversion of text obtained from `readLine()` into
numeric operands.

Initial source/example inspection did not reveal an obvious public conversion
API.

A direct compiler probe was therefore performed:

```kof
main() {
    var value = "10".toInt()
    println(value)
}
```

`kof check` result:

```text
checked 1 file(s) ? no errors
```

Result at checker level:

**PASS**

The same source was then executed using `kof run`.

Runtime result:

```text
Exception in thread "main" java.lang.NoSuchMethodError:
'java.lang.Object java.lang.String.toInt()'

    at Default.Main.main(numeric_conversion_probe.kf:2)
```

Result at runtime level:

**FAIL**

This establishes a reproducible checker/runtime inconsistency.

`String.toInt()` is accepted by `kof check`, but the generated JVM program
attempts to invoke a method that is unavailable at runtime.

See:

- OBS-010

### F4.4c — Interactive calculator

Status:

**BLOCKED**

The blocking condition is currently numeric conversion of values obtained
through `readLine()`.

This does not yet establish that interactive numeric input is impossible in
Kof.

It establishes only that the investigated `String.toInt()` path cannot be
used successfully on the tested Kof 0.0.7-alpha JVM toolchain.

Further conversion paths may still be investigated.

# Current Experimental Finding

The experiment has progressed beyond basic syntax validation.

Kof 0.0.7-alpha has successfully supported enough functionality to implement
the non-interactive calculator core:

- arithmetic;
- typed functions;
- function calls;
- conditional dispatch;
- explicit returns;
- exception throwing;
- exception handling;
- standard output;
- standard input.

The current boundary was found when connecting textual standard input to
numeric calculator operands.

The important result is not merely that the tested conversion failed.

The stronger finding is that:

```text
String.toInt()
      |
      +-- kof check --> PASS
      |
      +-- kof run ----> java.lang.NoSuchMethodError
```

Therefore the experiment has produced a concrete case in which semantic
checking and JVM runtime behavior disagree.

# Next Step

Investigate whether Kof 0.0.7-alpha exposes another supported conversion path
from `String` to `Int`.

Candidate forms must be tested independently rather than inferred from
`String.toInt()`.

If a working conversion path is found, continue to F4.4c and construct the
interactive calculator.

If no supported path is found, record the limitation and close F4.4 with the
interactive calculator blocked by the available numeric-input capabilities.
